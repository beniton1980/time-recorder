# AI共同開発 共通デザイン基準

版：v0.11 / 画面品質基準 v0.4 / 更新：2026-11-06

正本：[開発手法の詳細手順](https://app.notion.com/p/3f7f4b5e813281d7a792f7b00128d886) §4・§5-1・§6-1a・§6-2・§7-1a。これは試作・UI改修で使う要約配布版。基準変更時は正本と適用先を対応付ける。個別案件の業務仕様・権限・必須検証・公開条件を優先し、このファイルを包括的な実行許可にしない。

## 役割と着手

- 人は課題・目指す成果・現場の声を示し、価値・優先順位・業務上の合否を判断する。AIはそれを具体的な画面・操作へ翻訳し、必要な見本の作成、実装、提示前の点検まで担う。
- 人がFigma、ワイヤーフレーム、細かな寸法を用意することを前提にしない。AIが課題から仮の達成条件と初稿を作り、反応から目指す体験を具体化する。既知の情報を聞き直さない。
- AIが今回の段階（構造・動線／利用可能な状態／仕上げ）、判断する問い、完成条件、維持する条件、対象画面・状態・端末、今回は磨かない部分を既存記録へ短くまとめる。新しい質問票や書式承認を増やさない。

## 工程と提示物

基本は、課題・完成条件 → ワイヤーフレーム（情報構成・操作順）→ 参考画像（文字・配色・余白を含む完成像）→ 動くモック（操作・状態・復帰）→ 本実装・確認。AIが用意し、未決事項と影響に応じて工程を選ぶ。

| 区分 | 判断する条件 | 利用者へ提示するもの |
| --- | --- | --- |
| 構造・方向性から検討 | 新しい画面・主要動線、情報の優先順位や構成が未定、構造に関する繰り返す違和感 | ワイヤーフレーム → 参考画像 → 動くモックを本実装前に提示。採用済みのデザイン見本は再利用可。 |
| 局所的なUI変更 | 大枠は確定しているが、案内・入力・カード等の配置・強弱・操作に判断が残る | 対象部分の差分画像・小さな試作を本実装前に提示。構成と見た目を1枚にまとめ、変わる操作は既存画面を使った局所モックで確認できる。 |
| 軽微な変更 | 目的・主要動線・情報の優先順位・状態の意味が不変。既存部品内の誤字・余白等で、業務結果・保存・確定・権限・金額・重要な判断に影響せず、方針に未決事項がない | 独立した試作は省略可。対象端末で変更前後の実表示を確認し、比較画像を提示する。 |

- 軽微は上記の全条件を満たす場合だけ。行数や実装の容易さでは決めない。少数行でも押す順番・注意の強さ・承認や送信の意味が変われば局所変更以上。影響が不明なら対象を絞って調査・試作する。工程の簡略化で業務・安全の必須検証を省かない。
- 既存見本の再利用や、参考画像とモックの統合は可能。選んだ区分・最初に提示するもの・省略する工程と理由を既存記録へ1〜3行で示す。既存合意の範囲は進め、人に残る業務・体験上の判断だけを確認する。
- 提示とは、利用者がチャット上の画像や閲覧可能なリンクから判断できる状態。内部で作成・点検・保存しただけでは提示済みにしない。見本の参照・対象版・端末・判断する点を残す。未提示は理由付きで明示し、見本が必要な判断を完了扱いにしない。実装後の画像を実装前の提示の代わりにしない。
- 画像生成の参考画像は完成像の検討材料。未決の内容は仮と示し、操作・保存・認証の検証済み証拠にはしない。モックは隔離環境・架空データを使い、仮の接続と実際の確認範囲を分ける。秘密値・不要な個人情報を見本や記録に残さない。
- 通常は推奨1案から始め、複数案は正本§5-1aの条件で選ぶ。P1候補は判断できる粗い案までとし、採用前の完成実装は求めない。

## 読み取りやすさと整合性

同じ役割はそろえ、違う役割は見分けられるようにする。寸法がそろっただけで分かりやすいとは判定しない。

1. **読む順番を作る。** 主情報・補足・詳細の強さを配置、文字の大きさ・太さ、背景で分ける。業務で探す情報を優先し、すべてを同じ強さで強調しない。補足も読める濃さを保つ。
2. **まとまりを示す。** 関係する情報を近づけ、別のまとまりとの間を広くする。見出しは説明する内容に近づける。同じ余白を全要素へ一律に適用しない。
3. **寸法と整列を整える。** 同じ役割・操作群の部品は寸法、端、文字の基準線をそろえる。役割や情報量に理由のある差は保つ。数値差だけを不具合の根拠にしない。
4. **背景と枠に役割を持たせる。** 画面の地、主な作業、補足の関係を示す。同じ白い面が続いて区切りが曖昧なら、淡い背景差・余白・見出しを使い分ける。枠は必要なまとまりに使い、項目ごとの枠や入れ子を増やす前に配置で整理する。白を減らすためだけに色分けしない。
5. **強調と状態の意味をそろえる。** 主な操作、選択中、注意・失敗などに表現を割り当てる。同じ意味には同じ表現を使い、色だけでなく言葉や形も添える。読取り・部品識別に必要なコントラストを保つ。
6. **仕事に合わせて密度を変える。** 一覧の比較は視線が行き来しやすい間隔、入力や判断の区切りはまとまりが分かる余白にする。全画面を一律の広さ・密度にしない。
7. **操作と結果をつなぐ。** 聞く・考える順に入力し、確認・保存・確定・発行を区別する。処理中・成功・失敗と次の行動を操作した場所で伝え、入力保持と復帰を確認する。
8. **実際の端末と状態で見る。** 対象端末の実表示で、長文、折り返し、空・読込み中・失敗など関係する状態を確認する。スマホはブラウザーとホーム画面追加時の高さを分ける。紙は原寸の出力で必要な仕事を確かめる。未確認は明示する。

言葉の短さ、最頻操作、端末・紙での品質など、既存の詳細基準は正本§4-2を必要な範囲で参照する。具体的な色・書体・寸法を全案件の固定値にしない。

## 案件の部品・見本との接続

- 着手時に、今回使う共通部品・共通値の場所、どの役割・端末・状態で使うか、採用済み見本と参照版を確認する。既存の案件資料へ参照をまとめればよく、網羅的なカタログを開始条件にしない。
- ワイヤーフレームからは情報構成を読み、部品の見た目・振る舞いは現行仕様と採用済み部品に従う。矛盾は参照元と版を照合する。
- 対応部品がなければ、AIが今回の目的と既存設計に沿って追加案を作る。既存部品が無視された場合は、基準不足・参照漏れ・優先関係・実装への未反映を切り分ける。
- 寸法や色の値は実装側の共通値を参照し、文章へ二重に転記し続けない。画像の再現と操作の成立は別々に確かめる。

## 段階に合わせたレビューと終了

評議会は必要な複数の視点で確認する任意の方法。小改修で必須にせず、対象案件の権限と依頼範囲の中で必要な役割だけを使う。

| 段階 | 主に評価すること | 成果を妨げない限り後へ送ること |
| --- | --- | --- |
| 構造・動線 | 情報のまとまり、優先順位、入口、主要な操作の流れ、案の成立条件 | 構造選択に影響しない微細な寸法や装飾 |
| 利用可能な状態 | 代表的な操作、保存・確定・復帰、必要な状態、端末、読取り・誤操作 | 独立した機能追加、成果を左右しない表現上の好み |
| 仕上げ | 価値を認めて選んだ範囲の余白・文字・色・動き | 範囲を越える作り直しや追加候補 |

早い段階でも読み取りや操作に関係する基本品質を守る。データ・権限・保存等の必須条件や必要な検証を、この区分で省略しない。

1. **議題と上限を決める。** 通常は初回レビュー1回と、採用した修正の確認1回。長い検討が必要なら、開始前に時間・回数の上限を示す。満点までの自動反復をしない。
2. **独立して所見を出す。** 必要な視点だけを選び、他担当の結論や期待得点を先に渡さない。仕様確認には対象版・基準を渡す。利用者役には目的・既知の情報・開始状態を渡し、正解の操作順や実装説明を渡さない。独立した文脈がない場合は限界を明示する。
3. **今直す理由を示す。** 対象、起きる条件、誰のどの仕事への影響、関係する完成条件を示す。事実と仮説を分ける。「さらに良くなる」だけで必須修正にしない。
4. **統合担当が採否を決める。** 再現・重複・影響を確かめ、「今回直す／後で検討する／採用しない」と理由を既存記録へ残す。全指摘の相互批評を続けず、判断を変える対立点だけ追加確認する。既存合意内の採否はAIが行い、残る業務・体験上の選択だけを人へまとめて戻す。
5. **修正確認を限定する。** 採用した指摘の解消と、修正による不具合・周辺への影響を確かめる。全面的な改善案の募集を再開しない。未解消の必須事項は、対象を絞って修正・再確認する。
6. **完成条件で閉じる。** 今回の成果・必要な検証に加え、利用者へ提示した見本の参照・対象版・工程の省略理由を確認する。構造・方向性と局所変更は本実装前、軽微な変更は完了報告までの提示を確かめる。採用見本と仕様・実装の差異と理由を確認し、未解決の必須事項がなければ区切る。満点・全員一致・全候補の消化は条件にしない。再開は、完成条件を満たせない新事実、重大な問題、または価値を認めて追加範囲を選んだときに限り、理由・範囲・上限を示す。上限に達して必須事項が残れば未完了として状況と選択肢を報告する。

残る案は実施の約束にせず、価値がある候補だけ次の選択へ渡す。点数は補助情報であり、具体的な指摘・根拠・利用者への影響を添える。AIの合意を実利用での効果と扱わない。

## 現場の声を次の初稿へ戻す

- 元の声、起きた場面、対象版を既存の記録へ残す。解決案がなくても受け取り、頻度・原因・効果が不明なら推測で埋めない。
- AIが原因と改善案を整理し、修正後に元の困りごとへの対処と通常操作を確認する。AIの検証と実利用の結果を区別する。
- 学びは、目的・適用条件・見直す条件を添えて、共通基準・部品・見本・検証のうち原因に合う箇所へ戻す。案件固有の事情は案件仕様に残す。一般化の根拠が弱ければ対象を限定して試す。
- 初稿が過去の指摘を踏まえたか、既知の問題が再発したか、同じ説明・修正が減ったか、維持負担が見合ったかを見る。新しい発見と既知の再発を区別し、ルール数や得点を成果にしない。
- 正本を更新したら、今回の適用先の.md・見本・部品との対応を確かめ、未反映を明示する。重要な判断は既存の判断・評価DBの同じレコードを育て、新しい日報や細かな声ごとの行を増やさない。

## 次のUI改修1件で確かめること

AIが今回の問い・区分・最初に見せるものを短く示し、この基準と案件の部品・見本から初稿を作る。必要な時点で催促なしに見本を提示できたか、軽微な変更で工程を増やしすぎなかったか、未決の判断を解消できたかを既存記録へ返す。必要なレビューは上記の範囲で閉じる。

試作の区切りで、初稿の読み取りやすさ、同じ指摘の再発、レビューが些細な修正へ拡大しなかったか、説明・記録の負担を既存記録に短く残す。1件の試作から一般的な効果を実証したとは扱わない。
