# ONOGAMI 勤怠

有限会社魚時のスタッフ向け勤怠管理システムです。

## 主な機能

- LINE LIFFによるスタッフ認証
- 店舗QRコードを使った出勤・休憩・退勤の打刻
- 打刻時の位置情報による店舗からの距離確認（正確な座標は保存せず、判定結果のみ保持）
- 打刻履歴の保持と訂正申請
- 管理者による勤務状況確認・訂正承認・直接修正
- 営業日およびスタッフ別の履歴確認

## 構成

- Next.js App Router
- Vercel
- Neon Postgres
- LINE LIFF

## 店舗オンボーディング

限定提供版の申請・承認APIを有効にする前に、次を設定します。

1. `db/migrations/0006_onboarding_requests.sql` を対象DBへ適用
2. VercelのProduction / Previewへ `ONOGAMI_OPERATOR_LINE_USER_IDS` を追加
3. 値には店舗申請を確認できるONOGAMI運営者のLINE user IDをカンマ区切りで設定

この変数はサーバーだけで参照し、`NEXT_PUBLIC_`は付けません。未設定の場合、運営者用APIは安全側に倒れて利用できません。

## Preview環境の安全設定

`.env.example`にはキー名だけを記載し、秘密値は`.env.local`またはVercelの環境変数へ設定します。

Vercel PreviewのDBアクセスは、専用Neon branchを割り当てた後にPreviewだけへ`ONOGAMI_PREVIEW_DATABASE_ISOLATED=true`と`ONOGAMI_PRODUCTION_DATABASE_HOST`を設定するまで停止します。本番DBと同じホストの場合も停止します。

Previewのメール送信は既定で停止し、安全なテスト送信先を準備した場合だけ`ONOGAMI_PREVIEW_EMAIL_ENABLED=true`で許可します。

スタッフのLINE実機確認では、同じLINE Loginチャネルに検証専用LIFFを作り、そのIDを対象ブランチのPreview限定で`NEXT_PUBLIC_ATTENDANCE_LIFF_ID`へ設定します。Endpointは対象PreviewのルートURL（末尾`/`）、Full、scopeは`openid`だけとし、検証専用店舗のQRを使います。打刻画面と`/liff-entry`がこのIDを使い、未設定時は既存の本番IDを維持します。認証チャネル自体は変わりません。管理画面・オンボーディングの入口はこの設定の対象外です。本番LIFFのEndpointを検証先へ変更しません。

管理者の勤怠修正を実機確認する場合は、同じLINE Loginチャネルに管理者検証専用LIFFを作り、対象ブランチのPreview限定で`NEXT_PUBLIC_MANAGER_LIFF_ID`へ設定します。Endpointは対象Previewの`/manager`（末尾`/`なし）、Full、scopeは`openid`だけとします。入口QRは`https://liff.line.me/{検証用LIFF ID}`とし、末尾に`/manager`を重ねません。管理者トップ、個人勤怠、個人勤怠の編集の3画面がこのIDで初期化され、未設定時は既存の本番IDを維持します。管理者権限は検証DBの所属と既存APIで確認し、認証を迂回しません。

この設定がある場合だけ、3画面に検証用の表示を付け、管理者トップは勤怠確認に絞ります。本番LIFFへ移動し得るQR管理・掲示・店舗設定・給与等の入口は表示せず、共同管理者の案内共有も無効にします。勤怠リンク生成に必要なQRアンカーは非表示でDOMに保持します。未設定時の本番画面は変わりません。

この管理者検証入口から`/liff-entry/manager`は通りません。旧入口や対象外画面をURL指定で開く用途には対応していません。本番のリッチメニューからは従来の本番環境が開きます。検証には専用QRを使い、PreviewへのDB分離・メール停止は引き続き必須です。

## 本番DBの権限分離

`db/migrations/0017_least_privilege_app_role.sql` は、所有者権限を持たない`onogami_app`権限グループを作成し、ONOGAMI固有関数の`PUBLIC`実行権限を取り消します。アプリ接続の切り替え時は、リポジトリへパスワードを保存せず、Neonで専用LOGINロールを別途作成して`onogami_app`へ所属させ、その接続URLをVercel Productionの`DATABASE_URL`へ設定します。`neondb_owner`はマイグレーション専用としてアプリから分離します。

復旧・新環境の構築では、0017と0018を個別に適用せず、`db/recovery/0017_0018_least_privilege_atomic.sql`を`psql`で1回だけ適用します。このファイルはエラー時に停止し、両変更を単一トランザクションで確定するため、広い暫定権限のまま処理が終わる状態を防ぎます。通常の適用履歴では、すでに適用済みの0017・0018を再実行しません。

アプリは`DATABASE_URL`だけを参照し、Neon連携が作成する所有者接続変数へフォールバックしません。ProductionとPreviewには、それぞれ最小権限ロールと分離済みDB branchの`DATABASE_URL`を必ず設定します。未設定時は所有者接続へ戻らず、安全側に停止します。

## 打刻・訂正の保存結果の回復

打刻と本人の訂正申請は、1回の操作に同じ`clientRequestId`を使います。送信結果が不明な間は別の打刻・訂正を止め、bootstrapで本人・店舗に属する保存結果、勤務状態、履歴をまとめて取り直します。再読み込みでは確認だけを行い、未保存の操作を自動送信しません。自己登録も応答の成否だけで判断せず、有効な所属を再取得します。

未確認の操作内容はそのタブの`sessionStorage`に保持し、確認後に消します。LINE認証・QR・GPS・氏名欄は保持しませんが、「その他」の申請文は同じ内容を再送するために必要です。タブを閉じた場合やストレージを利用できない環境では、再読み込みを越える操作識別の保持は保証しません。

新規打刻にはbootstrapの`state_version`を`expectedStateVersion`として付け、再試行でも固定します。DBの状態行をロックする同じクエリで照合し、他画面の操作で勤務状態が一巡した場合も古い操作を追加しません。保存済みIDの結果照会・再送は古い版の要求でも可能です。打刻・訂正・登録と結果確認のHTTP待機はそれぞれ15秒で打ち切ります。タイムアウトを保存失敗とは見なさず、同じ操作IDを保持して結果確認へ進みます。

### 移行と公開の順序

1. Owner確認の後、公開先DBに`0040_staff_correction_idempotency.sql`を先に適用します。既存履歴は保持し、列・部分一意索引・本人訂正関数を追加します。
2. 新コードを公開します。新bootstrapも新しい列を参照するため、コードだけの先行公開はできません。
3. 開いたままの旧画面は再読み込みします。操作ID・対象打刻・変更先を指定しない旧訂正リクエスト、および状態版を持たない未保存の打刻リクエストは400で拒否します。旧打刻の保存済みIDは引き続き結果確認できます。

アプリを戻す場合も追加済みの列と保存済み履歴は残します。旧アプリへの巻戻しは旧来の再送不具合も戻すため、復旧判断時に区別してください。DBの破壊的な巻戻しはこの手順に含めません。

### 押し忘れの整合性・休憩一組の移行（0041）

新環境への導入では、Ownerの最終承認後、0040適用済みの公開先DBへ`db/migrations/0041_missed_correction_consistency.sql`を先に適用し、その後に対応するアプリを公開します。新コードは`group_id`と新しい検証関数を参照するため、コードだけを先行公開しません。既に0041が適用された環境には再実行しません。

0041は既存履歴を保持し、押し忘れの申請時・承認直前に対象時刻前後の整合性を検証します。休憩開始と終了は2件のADDを一組として保存し、承認・却下を同じトランザクションで行います。旧9引数の本人訂正関数も新関数へ委譲するため検査を迂回できず、0040で保存済みの操作ID・内容による結果回復と再試行は継続できます。

押し忘れは既に行った勤務の申告なので、単独打刻・休憩の開始と終了ともDBの現在時刻を超える日時は受け付けません。申請前の確認、保存、ADD／REVIEWの承認で同じ条件を検査し、従来の未来5分の許容は廃止します。過去62日の申請範囲と保存済み操作の結果回復は維持します。0041を先行適用した検証環境では、最終版の`validate_correction_addition`を`CREATE OR REPLACE FUNCTION`で更新し、列・索引の追加を含む0041全体を再実行しません。

アプリを切り戻す場合も0041の列・関数・履歴を残します。DBを旧版へ戻すと一組の原子的な承認・却下を失うため、DBのダウングレードは行いません。旧画面は一組の表示に対応しないため、アプリの切戻し時は未確認操作・未処理申請への影響を確認します。隔離Neonでは架空データと実際のアプリ権限による同時送信・承認を検証済みです。本番適用・LINE実機受入とは区別します。

### 管理者の直接修正の日時制限（0042）

管理者のADD／REPLACEも、DBの現在時刻を超える日時を拒否します。VOIDでは日時を追加しないため、既に保存された未来の誤記録も取り消せます。個人勤怠の編集は実際の打刻日・時刻（日本時間）を初期表示し、営業日を実日付として代入しません。保存後は作業を始めた勤怠月へ戻ります。日付を別月へ変更した場合の所属月は、既存の営業日計算に従います。

個人勤怠へ戻る際は、対象営業日へのスクロール・フォーカスと「要確認のみ」の選択を引き継ぎます。修正により絞込み対象外になった日は、案内の「修正した日を確認」から開けます。保存API成功時だけ、同一タブの一回限り・30分有効のsessionStorage記録とURLの識別子を照合し、追加・変更・取消を区別して案内します。URLのみ・再読込・期限切れでは保存成功を断定せず、保存記録を保持できないブラウザーでも対象日へ戻ります。

勤務記録のない日は日付・「勤務記録なし」と修正入口を左右にまとめ、全日付を残します。狭い幅では日付と状態が折り返し、修正リンクは高さ44px以上を保ちます。リンクの読み上げ名には対象日を含めます。最後の打刻を取り消して記録なしに戻っても、対象日のフォーカスと保存通知を保持します。勤務予定を持たないため、休み・欠勤・打刻忘れとは判定しません。

個人勤怠一覧の出退勤・休憩は、APIの実打刻日時を店舗の`timezone`で表示します。営業日と異なる日付だけ「翌日 02:00（10/9）」のように実日付を添え、2日以上は日数、年をまたぐ場合は年も表示します。時刻の大小から翌日とは推測しません。同日の時刻と既存の表示精度（出退勤は分、休憩明細は秒）を保ち、休憩は一組ごとに表示します。旧応答でタイムゾーンがない場合や不正な日時は、既存の時刻表示へ戻します。共通PDF／CSV・日別SSoT・保存時の営業日計算には影響しません。

`node --test tests/manager-attendance-display.test.mjs tests/manager-attendance-return.test.mjs`で、同日・翌日・月年跨ぎ・複数日・店舗時差・未終了休憩、隔離APIの集計維持、修正後の対象日と絞込みを確認します。

保存後の一覧取得に失敗した場合は、保存済みと読込み失敗を分け、「もう一度読み込む」は一覧の再取得だけを行います。スタッフ・月の切替中／取得失敗時は日別一覧と修正リンクを表示せず、選択中の店舗・スタッフ・月と一致する応答だけを表示します。APIの保存内容・権限・集計、DB構造、環境変数の変更はありません。回帰確認は `tests/manager-attendance-return.test.mjs` と `tests/manager-correction-screen.test.mjs`、LINE初期化とPreview導線は `tests/manager-liff-preview.test.mjs` を使います。

公開時は07の手順に従い、Ownerの最終承認・復旧用ブランチ作成の後、0041適用済みの対象DBへ`db/migrations/0042_manager_correction_time.sql`を単一トランザクションで適用します。既存データ・RLS・関数のSECURITY INVOKERとEXECUTE権限が変わらないことを確認してから、対応アプリを公開します。アプリだけでは未来日時制限は成立しません。

0042は管理者直接修正関数の未来日時ガードだけを追加し、既存データを変更しません。アプリ切戻しでもDBのガードを保持します。旧アプリでは拒否理由が汎用エラーになるため、画面表示の違いを考慮してください。Test Centerには隔離環境で行う未来拒否・日跨ぎ編集の実機確認項目を設けています。

### 共同管理者の日常操作（0043）

有効な共同管理権限を持つ在籍スタッフは、既存の管理画面アクセスと同じ条件で直接修正・申請判断・月次帳票一覧／CSV／再発行／テスト送信・店舗QR操作を行えます。本人・店舗・所属状態・権限は既存の`app_manager_store_allowed`で確認します。権限なしの帳票一覧は403を返し、権限がある場合の未発行一覧は空の200を返します。宛先の確認・同意、再発行の重複防止、未来日時拒否は維持します。

公開時は07の手順に従い、Ownerの最終承認・復旧用ブランチ作成の後、0042適用済みの対象DBへ`db/migrations/0043_co_manager_operations.sql`を先に適用し、対応アプリを公開します。0043は訂正用の2関数の管理者判定のみを変更し、既存データ・RLS・SECURITY INVOKER・EXECUTE権限を保持します。コードだけを公開すると共同管理者の訂正保存がDBで拒否されるため、先行公開しません。

### 締め日変更前の月次帳票

管理画面のCSV取得・再発行は一覧の送信履歴ID（`reportId`）を送り、同じ店舗の送信済み初回履歴に保存された対象期間を使います。現在の締め日設定では再計算しません。旧画面の`periodEnd`指定も、該当履歴が1件に定まる場合だけ受け付けます。再発行は既存仕様どおり訂正後の最新勤怠でPDFを作り、確認・同意済みの現行宛先へ送ります。初回送信履歴は保持します。

新しい月次締めとテスト送信は現在の締め日設定を使い、Cronの失敗分再試行は既存の保存済み期間を使います。この修正のDB migration・環境変数変更はありません。

### 停止・退社したスタッフの過去勤怠

スタッフ管理から、利用再開・再雇用をせずに停止・退社者の個人勤怠へ移動し、打刻の追加・変更・取消を行えます。個人勤怠の選択肢には所属状態を表示し、退社者を末尾に並べます。操作する管理者・共同管理者は引き続き有効な所属と同じ店舗の管理権限が必要です。

### 一覧にない過去期間の月次帳票（F08・0044）

管理画面の月次勤怠表で対象月を選び、正式PDF・補助CSVを取得できます。その月に初回送信済みの履歴があれば保存済み期間を優先し、複数あるときは明示選択します。直近12件より古い履歴も対象月で照会します。履歴のない月は現在の締め日を初期表示し、当時と違う場合はその帳票だけ月末・15日・25日締めへ変更できます。期間の計算は既存の締め日計算を再利用し、店舗設定は変更しません。月の照会失敗時は推測した期間で取得せず、再試行を案内します。

例外的な開始日・終了日の指定は「期間を調整」内に置きます。対象は店舗の現在日より前の1〜31日間（既存の月次PDFレイアウト内）。日別確定勤怠SSoTから最新の訂正を反映し、有効な同店舗の管理者・共同管理者だけが操作できます。送信先未確認でも取得でき、保存済み履歴は変更しません。

取得は配信履歴を作りません。「この期間をメール送信」の確認操作では、確認・同意済みの現行宛先世代を検査し、通常Cronと同じ`initial`の期間キーで送信します。同じ開始日・終了日の連打、並行Cron、送信後応答消失の再試行は重複送信しません。初回送信済みなら一覧の再発行を使います。失敗した明示送信は既存の初回再試行対象になり、保存済み期間と試行履歴を保ちます。送信先を確認しただけで記録のない過去期間を一括送信することはありません。

### 退勤申請待ちの次勤務開始（F04・0045）

前回の具体的な退勤漏れ申請が1件特定でき、同じ店舗の翌営業日以降である場合は「次の勤務を開始」から新しい出勤を記録できます。申請はPENDINGのまま、新出勤の`previous_checkout_request_id`で関連を保持します。前回分は未確定、却下後も新出勤を保持します。日付変更だけの勤務終了、休憩未終了や時刻不明相談、同一営業日の連続出勤、他店舗勤務中の出勤は許可しません。夜勤を継続する退勤・休憩操作は残します。

打刻transactionは本人のadvisory lockに続いてstate→申請行の順にロックし、その後の新しいsnapshotで申請・状態版・本人・QR・他店舗勤務を再確認します。開始直前の承認／却下は古い開始操作を拒否して再読込みし、開始後の判断は新出勤を消しません。操作IDの再送は申請IDも照合します。日別集計は既存の営業日単位を使い、前回分が未解決でも新勤務を独立して集計します。

公開は今回のOwner最終承認と07の復旧branchを確保した後、0044適用済みDBへ`db/migrations/0045_pending_shift_start.sql`を単一transactionで先に適用します。追加はnullable列・同スタッフ同店舗FK・CHECK・一意索引・SECURITY INVOKERの読取り関数です。既存イベント／申請／状態、RLSと権限を前後照合し、列追加を除くデータが不変であることを確認します。環境変数変更なし。新アプリは0045が必要で、アプリ切戻し時も0045と記録を保持します。旧アプリは次勤務開始の入口を持ちませんが、保存済み新勤務の通常操作は継続できます。DB復元・関連列の削除は別判断です。

`node --test tests/pending-shift-start.test.mjs tests/punch-screen-flow.test.mjs`で申請→開始→承認／却下、再送・古い状態、夜勤・営業日・店舗境界・集計を確認します。Neon隔離DBでは実PostgreSQLの競合、移行失敗のtransaction rollback、0044アプリと0045 DBの互換も確認します。

### 営業日をまたぐ管理者訂正（0046）

退勤・休憩の所属営業日は、訂正を反映した出勤の営業日を引き継ぎます。例えば9/30 22:00の出勤に対する退勤を10/1 04:59から05:01へ変更しても、9月の勤務7時間1分として集計します。出勤を10/1 05:00から04:59へ動かす場合は、退勤・休憩も9/30営業日へ移ります。出勤がない打刻や既に終了した勤務の後の孤立打刻を、無関係な過去の勤務へ結び付けません。

`0046_correction_business_day.sql`は有効打刻viewを統一し、管理者直接修正の保存transaction内でstate行をロックして、変更前後の影響日・重複時刻・打刻順序を検査します。既存の不整合の段階的な修復は可能ですが、REPLACEで完了済みの勤務を新たに未退勤へ分割する変更は拒否し、履歴・状態の変更をrollbackします。ADD・VOIDによる未完成状態、未来拒否、停止・退社者の修正、共同管理者と店舗境界は維持します。

申請待ちは確定打刻にせず、現在の出勤に対応する営業日へ要確認を表示します。申請時の`requested_business_date`を書き換えず、個人勤怠／月次集計・承認画面の参考履歴・F04の次勤務開始判定で共通の読取り関数を使用します。日別計算・PDF／CSVの集計式、締め期間、メール送信の条件は変更しません。

本番反映には今回のOwner最終承認が別途必要です。07に従い復旧branchを確保し、DB0045へ0046を単一transactionで先行適用してからアプリを公開します。22表のデータfingerprint、既存view／関数のACL・SECURITY INVOKER・RLSを前後照合します。元の打刻・申請履歴は更新しませんが、有効打刻の営業日と再取得する日別／月次結果は過去の訂正も含めて変わり得ます。公開前に旧／新viewの差分件数・期間と集計への影響を確認してください。送信済みメールを再送せず、配信履歴も変更しません。

新アプリは0046の読取り関数が必要です。アプリ切戻しでも0046と保存履歴を保持します。旧アプリでは変更前の事前検査・申請日表示が戻るため、営業日境界をまたぐ訂正の完全な復旧とは扱いません。DB復元は別判断で、viewを戻すだけでも旧来の分割が再発します。環境変数・テーブル構造の変更はありません。

`node --test tests/correction-business-day.test.mjs`で04:59／05:00／05:01、出勤の月移動と逆方向、休憩・追加打刻・再訂正・取消、別勤務との交差・重複拒否、申請待ちの移動、F04、移行失敗時のrollbackと原本／ACL保持を検証します。全体回帰にはTest Centerの模擬勤怠・PDF／CSV／メール本文生成を含みます。実画面では架空の月末夜勤を変更し、保存通知・翌日の日付・日別／月次合計を確認します。実LINE／iPhoneと独立した利用者評価は別途必要です。

### 相談から打刻を修正して対応完了（0047）

未処理のREVIEWは「相談内容・対象の打刻を確認」から開き、同じスタッフの個人勤怠→既存の追加・変更・取消→相談へ戻る順に操作します。対象IDがない旧相談は受付月を検索の初期値に使い、対象を自動決定しません。対象IDがある場合は現在の営業日を解決します。通常の個人勤怠からの修正は従来の戻り先を保持します。

保存した訂正は`consultation_corrections`に変更前後・相談ID・訂正ID・再送IDを同じtransactionで追記します。保存だけでは相談を閉じません。「対応済みにする」は`consultation_resolutions`へ完了者・日時・結果を追記し、原相談・元打刻・過去の訂正を保持します。修正なしの場合は短い確認理由が必須です。完了は勤怠の強制確定ではなく、他の申請待ち・順序不整合は残ります。対応済み一覧は必要時に20件ずつ取得します。

原相談のPENDINGを保持するため、管理一覧・日別／月次・本人履歴・bootstrap・同じ申請の再送・旧承認APIは`correction_request_status`を共有します。本人には進捗・結果区分・日時だけを返し、内部対応理由・管理者情報を返しません。新しい通知やメール送信はありません。

修正・完了は有効な同店舗の管理者／共同管理者だけが行えます。state→相談行の順で排他し、読込み時のstate版が古ければ再確認を要求します。同じ再送ID・内容の修正と完了の再試行は保存済み結果を返します。旧承認関数からも、修正が結び付いた相談や完了済み相談を追加・却下へ変更できません。通常のADD・休憩一組の承認、停止・退社者の過去訂正、未来拒否、0046の勤務順序検査は維持します。

公開には今回のOwner最終承認が必要です。07の復旧branchを確保し、0046適用済みDBへ`db/migrations/0047_consultation_resolution.sql`を単一transactionで先行適用してから対応アプリを公開します。既存22表のfingerprintが不変、追加2表が空、全24表のRLSと新関数のSECURITY INVOKER・EXECUTE権限が適切であることを照合します。環境変数変更はありません。今回の検証では本番へ適用していません。

アプリ切戻しでも0047と保存履歴を残し、表削除・原相談の書換えで戻しません。旧アプリは完了履歴を読まず、完了済み相談を未処理・申請待ちとして表示し得ます（DBは再処理を拒否）。そのため利用開始後の旧版切戻しは完全互換ではなく、相談操作を止めて対応版を復旧する手順を別途判断します。DB全体の復元は別の承認事項です。

`tests/consultation-resolution.test.mjs`と`tests/consultation-screen.test.mjs`で、対象未指定・月跨ぎ・複数訂正・修正不要、再送・不明結果の回復、他店舗拒否、原本保持、他の要確認の維持と完了後の各読取りの一致を確認します。実PostgreSQLでは移行／transaction rollback、RLS、同時保存・完了を架空データで検証します。実LINE／実機受入、独立した利用者役評価は別です。

### 本人の勤務確認と申請元の保存（P0・0048）

打刻画面の「勤務の確認」から、既存の押し忘れ申請・時刻不明の相談・本人限定の結果履歴へ進めます。通常の当営業日勤務は通知せず、前営業日から継続中の勤務は継続確認にします。「勤務を続けています」は同じタブ・同じ記録版の表示だけを折り畳み、勤務状態・時刻・申請を変更しません。通知の取得失敗は通常打刻を止めません。

`/api/attendance-attention`はLINE本人・有効QR・所属・店舗を検証し、本人の保持中データを一つのSQLスナップショットで読みます。日別SSoTの状態遷移を再利用して、申請待ちと不足を分けて20件ずつ返します。最新8打刻・最新20申請・62日の入力制限を通知の打切り条件にはしません。GPSだけの警告・勤務記録のない日を不足扱いにせず、シフト連携・外部プッシュ・既読管理は含みません。

`correction_attention_sources`は、申請IDと本人・店舗、通知元の実効出勤等のID、対象日の記録版、申請時点の勤務文脈を保持します。複合FKとRLSを持ち、runtimeのUPDATE/DELETEは不可です。新しい保存関数は申請と関連を同じトランザクションで保存し、既存のスタッフ状態ロックで別タブ・管理者処理と直列化します。同じclientRequestIdの再送は保存済み内容を先に照合し、未保存の古い記録版は409、対応する確認待ち申請は既存IDで案内します。既存申請本文・打刻原本・営業日計算・承認処理は保持します。

管理者相談では通知対象日を受付日と別に表示し、既存の個人勤怠編集へ接続します。修正保存と相談完了は別のままです。対象の取消・移動後も申請時点の文脈を残し、対象未指定の旧相談を推測で結び付けません。結果履歴のrequestId指定は本人・店舗制約内で検索し、最新20件より古い申請にも到達します。

公開時はOwner最終承認と07の手順に従い、復旧branch確保→0047適用済みDBへ`db/migrations/0048_staff_attendance_attention.sql`を単一トランザクションで先行適用→新規表のRLS・FK・権限と既存データ不変を照合→対応アプリを公開します。環境変数追加はありません。旧アプリは新しい関連を読まないため、切戻しでも0048と保存済み関連を残し、対象との接続や重複案内が弱くなる影響を確認します。表削除やDB全体復元で戻す操作とは分けます。
