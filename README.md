# ONOGAMI 勤怠

有限会社魚時のスタッフ向け勤怠管理システムです。

## 主な機能

- LINE LIFFによるスタッフ認証
- 店舗QRコードを使った出勤・休憩・退勤の打刻
- 打刻時の位置情報による店舗からの距離確認（正確な座標は保存せず、判定結果のみ保持）
- 打刻履歴の保持と訂正申請
- 管理者による勤務状況確認・訂正承認・直接修正
- 営業日およびスタッフ別の履歴確認

## 構成

- Next.js App Router
- Vercel
- Neon Postgres
- LINE LIFF

## 店舗オンボーディング

限定提供版の申請・承認APIを有効にする前に、次を設定します。

1. `db/migrations/0006_onboarding_requests.sql` を対象DBへ適用
2. VercelのProduction / Previewへ `ONOGAMI_OPERATOR_LINE_USER_IDS` を追加
3. 値には店舗申請を確認できるONOGAMI運営者のLINE user IDをカンマ区切りで設定

この変数はサーバーだけで参照し、`NEXT_PUBLIC_`は付けません。未設定の場合、運営者用APIは安全側に倒れて利用できません。

## Preview環境の安全設定

`.env.example`にはキー名だけを記載し、秘密値は`.env.local`またはVercelの環境変数へ設定します。

Vercel PreviewのDBアクセスは、専用Neon branchを割り当てた後にPreviewだけへ`ONOGAMI_PREVIEW_DATABASE_ISOLATED=true`と`ONOGAMI_PRODUCTION_DATABASE_HOST`を設定するまで停止します。本番DBと同じホストの場合も停止します。

Previewのメール送信は既定で停止し、安全なテスト送信先を準備した場合だけ`ONOGAMI_PREVIEW_EMAIL_ENABLED=true`で許可します。

スタッフのLINE実機確認では、同じLINE Loginチャネルに検証専用LIFFを作り、そのIDを対象ブランチのPreview限定で`NEXT_PUBLIC_ATTENDANCE_LIFF_ID`へ設定します。Endpointは対象PreviewのルートURL（末尾`/`）、Full、scopeは`openid`だけとし、検証専用店舗のQRを使います。打刻画面と`/liff-entry`がこのIDを使い、未設定時は既存の本番IDを維持します。認証チャネル自体は変わりません。管理画面・オンボーディングの入口はこの設定の対象外です。本番LIFFのEndpointを検証先へ変更しません。

管理者の勤怠修正を実機確認する場合は、同じLINE Loginチャネルに管理者検証専用LIFFを作り、対象ブランチのPreview限定で`NEXT_PUBLIC_MANAGER_LIFF_ID`へ設定します。Endpointは対象Previewの`/manager`（末尾`/`なし）、Full、scopeは`openid`だけとします。入口QRは`https://liff.line.me/{検証用LIFF ID}`とし、末尾に`/manager`を重ねません。管理者トップ、個人勤怠、個人勤怠の編集の3画面がこのIDで初期化され、未設定時は既存の本番IDを維持します。管理者権限は検証DBの所属と既存APIで確認し、認証を迂回しません。

この設定がある場合だけ、3画面に検証用の表示を付け、管理者トップは勤怠確認に絞ります。本番LIFFへ移動し得るQR管理・掲示・店舗設定・給与等の入口は表示せず、共同管理者の案内共有も無効にします。勤怠リンク生成に必要なQRアンカーは非表示でDOMに保持します。未設定時の本番画面は変わりません。

この管理者検証入口から`/liff-entry/manager`は通りません。旧入口や対象外画面をURL指定で開く用途には対応していません。本番のリッチメニューからは従来の本番環境が開きます。検証には専用QRを使い、PreviewへのDB分離・メール停止は引き続き必須です。

## 本番DBの権限分離

`db/migrations/0017_least_privilege_app_role.sql` は、所有者権限を持たない`onogami_app`権限グループを作成し、ONOGAMI固有関数の`PUBLIC`実行権限を取り消します。アプリ接続の切り替え時は、リポジトリへパスワードを保存せず、Neonで専用LOGINロールを別途作成して`onogami_app`へ所属させ、その接続URLをVercel Productionの`DATABASE_URL`へ設定します。`neondb_owner`はマイグレーション専用としてアプリから分離します。

復旧・新環境の構築では、0017と0018を個別に適用せず、`db/recovery/0017_0018_least_privilege_atomic.sql`を`psql`で1回だけ適用します。このファイルはエラー時に停止し、両変更を単一トランザクションで確定するため、広い暫定権限のまま処理が終わる状態を防ぎます。通常の適用履歴では、すでに適用済みの0017・0018を再実行しません。

アプリは`DATABASE_URL`だけを参照し、Neon連携が作成する所有者接続変数へフォールバックしません。ProductionとPreviewには、それぞれ最小権限ロールと分離済みDB branchの`DATABASE_URL`を必ず設定します。未設定時は所有者接続へ戻らず、安全側に停止します。

## 打刻・訂正の保存結果の回復

打刻と本人の訂正申請は、1回の操作に同じ`clientRequestId`を使います。送信結果が不明な間は別の打刻・訂正を止め、bootstrapで本人・店舗に属する保存結果、勤務状態、履歴をまとめて取り直します。再読み込みでは確認だけを行い、未保存の操作を自動送信しません。自己登録も応答の成否だけで判断せず、有効な所属を再取得します。

未確認の操作内容はそのタブの`sessionStorage`に保持し、確認後に消します。LINE認証・QR・GPS・氏名欄は保持しませんが、「その他」の申請文は同じ内容を再送するために必要です。タブを閉じた場合やストレージを利用できない環境では、再読み込みを越える操作識別の保持は保証しません。

新規打刻にはbootstrapの`state_version`を`expectedStateVersion`として付け、再試行でも固定します。DBの状態行をロックする同じクエリで照合し、他画面の操作で勤務状態が一巡した場合も古い操作を追加しません。保存済みIDの結果照会・再送は古い版の要求でも可能です。打刻・訂正・登録と結果確認のHTTP待機はそれぞれ15秒で打ち切ります。タイムアウトを保存失敗とは見なさず、同じ操作IDを保持して結果確認へ進みます。

### 移行と公開の順序

1. Owner確認の後、公開先DBに`0040_staff_correction_idempotency.sql`を先に適用します。既存履歴は保持し、列・部分一意索引・本人訂正関数を追加します。
2. 新コードを公開します。新bootstrapも新しい列を参照するため、コードだけの先行公開はできません。
3. 開いたままの旧画面は再読み込みします。操作ID・対象打刻・変更先を指定しない旧訂正リクエスト、および状態版を持たない未保存の打刻リクエストは400で拒否します。旧打刻の保存済みIDは引き続き結果確認できます。

アプリを戻す場合も追加済みの列と保存済み履歴は残します。旧アプリへの巻戻しは旧来の再送不具合も戻すため、復旧判断時に区別してください。DBの破壊的な巻戻しはこの手順に含めません。

### 押し忘れの整合性・休憩一組の移行（0041）

新環境への導入では、Ownerの最終承認後、0040適用済みの公開先DBへ`db/migrations/0041_missed_correction_consistency.sql`を先に適用し、その後に対応するアプリを公開します。新コードは`group_id`と新しい検証関数を参照するため、コードだけを先行公開しません。既に0041が適用された環境には再実行しません。

0041は既存履歴を保持し、押し忘れの申請時・承認直前に対象時刻前後の整合性を検証します。休憩開始と終了は2件のADDを一組として保存し、承認・却下を同じトランザクションで行います。旧9引数の本人訂正関数も新関数へ委譲するため検査を迂回できず、0040で保存済みの操作ID・内容による結果回復と再試行は継続できます。

押し忘れは既に行った勤務の申告なので、単独打刻・休憩の開始と終了ともDBの現在時刻を超える日時は受け付けません。申請前の確認、保存、ADD／REVIEWの承認で同じ条件を検査し、従来の未来5分の許容は廃止します。過去62日の申請範囲と保存済み操作の結果回復は維持します。0041を先行適用した検証環境では、最終版の`validate_correction_addition`を`CREATE OR REPLACE FUNCTION`で更新し、列・索引の追加を含む0041全体を再実行しません。

アプリを切り戻す場合も0041の列・関数・履歴を残します。DBを旧版へ戻すと一組の原子的な承認・却下を失うため、DBのダウングレードは行いません。旧画面は一組の表示に対応しないため、アプリの切戻し時は未確認操作・未処理申請への影響を確認します。隔離Neonでは架空データと実際のアプリ権限による同時送信・承認を検証済みです。本番適用・LINE実機受入とは区別します。

### 管理者の直接修正の日時制限（0042）

管理者のADD／REPLACEも、DBの現在時刻を超える日時を拒否します。VOIDでは日時を追加しないため、既に保存された未来の誤記録も取り消せます。個人勤怠の編集は実際の打刻日・時刻（日本時間）を初期表示し、営業日を実日付として代入しません。保存後は作業を始めた勤怠月へ戻ります。日付を別月へ変更した場合の所属月は、既存の営業日計算に従います。

公開時は07の手順に従い、Ownerの最終承認・復旧用ブランチ作成の後、0041適用済みの対象DBへ`db/migrations/0042_manager_correction_time.sql`を単一トランザクションで適用します。既存データ・RLS・関数のSECURITY INVOKERとEXECUTE権限が変わらないことを確認してから、対応アプリを公開します。アプリだけでは未来日時制限は成立しません。

0042は管理者直接修正関数の未来日時ガードだけを追加し、既存データを変更しません。アプリ切戻しでもDBのガードを保持します。旧アプリでは拒否理由が汎用エラーになるため、画面表示の違いを考慮してください。Test Centerには隔離環境で行う未来拒否・日跨ぎ編集の実機確認項目を設けています。

### 共同管理者の日常操作（0043）

有効な共同管理権限を持つ在籍スタッフは、既存の管理画面アクセスと同じ条件で直接修正・申請判断・月次帳票一覧／CSV／再発行／テスト送信・店舗QR操作を行えます。本人・店舗・所属状態・権限は既存の`app_manager_store_allowed`で確認します。権限なしの帳票一覧は403を返し、権限がある場合の未発行一覧は空の200を返します。宛先の確認・同意、再発行の重複防止、未来日時拒否は維持します。

公開時は07の手順に従い、Ownerの最終承認・復旧用ブランチ作成の後、0042適用済みの対象DBへ`db/migrations/0043_co_manager_operations.sql`を先に適用し、対応アプリを公開します。0043は訂正用の2関数の管理者判定のみを変更し、既存データ・RLS・SECURITY INVOKER・EXECUTE権限を保持します。コードだけを公開すると共同管理者の訂正保存がDBで拒否されるため、先行公開しません。

アプリの切戻しでは0043と保存履歴を残します。0043を残した場合は共同管理権限を認めるDB判定も残るため、権限判定自体の切戻しが必要な障害では、Owner確認のうえで対象2関数の定義を0042／0041相当へ戻す手順を別途判断します。DB全体の復元や履歴削除は行いません。

### 締め日変更前の月次帳票

管理画面のCSV取得・再発行は一覧の送信履歴ID（`reportId`）を送り、同じ店舗の送信済み初回履歴に保存された対象期間を使います。現在の締め日設定では再計算しません。旧画面の`periodEnd`指定も、該当履歴が1件に定まる場合だけ受け付けます。再発行は既存仕様どおり訂正後の最新勤怠でPDFを作り、確認・同意済みの現行宛先へ送ります。初回送信履歴は保持します。

新しい月次締めとテスト送信は現在の締め日設定を使い、Cronの失敗分再試行は既存の保存済み期間を使います。この修正のDB migration・環境変数変更はありません。

### 停止・退社したスタッフの過去勤怠

スタッフ管理から、利用再開・再雇用をせずに停止・退社者の個人勤怠へ移動し、打刻の追加・変更・取消を行えます。個人勤怠の選択肢には所属状態を表示し、退社者を末尾に並べます。操作する管理者・共同管理者は引き続き有効な所属と同じ店舗の管理権限が必要です。

本人の打刻・自己再登録禁止、元打刻と訂正履歴、訂正した管理者の記録、状態遷移と未来日時拒否を維持します。入退社日の履歴がないため新しい在籍期間制限は加えず、管理者の既存の日時条件を使います。DB0043と互換性があり、この修正のmigration・環境変数変更はありません。

`node --test tests/former-staff-attendance.test.mjs`で、停止・退社者の閲覧・直接修正、本人操作禁止、他店舗・権限外・未来日時拒否、元打刻・監査の保持、既存申請承認とCSV集計を確認します。

### 一覧にない過去期間の月次帳票（F08・0044）

管理画面の月次勤怠表から開始日・終了日を明示指定し、送信履歴や送信先確認の有無にかかわらず正式PDF・補助CSVを取得できます。対象は店舗の現在日より前の1〜31日間（既存の月次PDFレイアウト内）です。現在の締め日から過去期間を推測せず、日別確定勤怠SSoTから最新の訂正を反映します。有効な同店舗の管理者・共同管理者だけが操作できます。

取得は配信履歴を作りません。「この期間をメール送信」の確認操作では、確認・同意済みの現行宛先世代を検査し、通常Cronと同じ`initial`の期間キーで送信します。同じ開始日・終了日の連打、並行Cron、送信後応答消失の再試行は重複送信しません。初回送信済みなら一覧の再発行を使います。失敗した明示送信は既存の初回再試行対象になり、保存済み期間と試行履歴を保ちます。送信先を確認しただけで記録のない過去期間を一括送信することはありません。

0044は共有claim関数の再試行時に`delivery_id`列と同名のOUT引数が衝突する既存エラー（42702）を、列の別名指定だけで修正します。関数の引数・SECURITY DEFINER・固定search_path・owner・権限、テーブル・データは変更しません。公開時は07に従い今回の最終承認と復旧branchを確保し、0043適用済みDBへ`db/migrations/0044_monthly_delivery_retry_column.sql`を単一トランザクションで先に適用します。既存データの集約fingerprint・関数owner/ACL/config・RLSを前後照合してください。アプリの切戻しでも0044と履歴を保持し、DB復元は別判断です。環境変数変更はありません。

`node --test tests/monthly-attendance-period.test.mjs tests/monthly-delivery-recovery.test.mjs tests/monthly-attendance-history.test.mjs`で未確認取得・明示送信・境界・訂正・権限・重複防止、0043の失敗再現→0044の移行・古いPROCESSING回復、F09の保存済み期間の互換を検証します。Test Centerの「送信先確認前の過去期間を取得・明示送信」に実画面手順を置いています。

`npm test`はPGliteの空DBへ全migrationを適用し、`onogami_app`と実際のRLSでAPI・状態・訂正履歴・店舗境界を確認します。保存前失敗／保存後応答消失／同一ID再送／再読み込み／二重タップは画面の回帰テストにも含めます。LINE本人確認とブラウザーのストレージ・権限挙動は実機で別途確認します。DB変更時はAGENTS.mdに従い、一時Neonブランチの架空データでも移行・同時実行を検証します。
